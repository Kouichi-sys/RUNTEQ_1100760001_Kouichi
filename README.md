# 現場映像確認・共有 Webアプリ

## 1. サービス概要

製造現場の監視カメラ(NxWitness)映像を、専用PCに依存せず社内LAN上のPCからWebブラウザで確認・共有できるようにするWebアプリです。トラブル発生時の映像をその場でクリップし、報告書作成や情報共有をスムーズに行えるようにすることを目指します。

製造ラインの技術員が抱える「専用PCでしか映像を確認できない」「映像共有に約20分かかる」という課題を、社内LAN上のどのPCからでもアクセスできる仕組みによって解決します。

---

## 2. 開発の背景

### 2-1. きっかけとなった体験

会社ではNxWitnessという監視カメラシステムを使用していますが、映像を確認できるのは専用PCのみで、週に2〜3回のペースで「専用PCが他の人に使われていて確認できない」という状況が発生していました。

また、トラブル発生時に映像を共有する場合、現場の専用PCまで移動し、該当映像を探し、スマホで画面を撮影し、メールに添付して自分のPCに送るという一連の作業に約20分かかっていました。この作業は自分だけでなく、社内のほとんどの人が同じように行っており、共通の悩みとなっていました。

### 2-2. なぜこの課題が気になったか

20分もの時間を映像共有だけに費やすことに、生産性の悪さと「無駄な作業をしている」という感覚を抱いていました。もともと仕事において非効率な部分が気になりやすい性格で、過去にも業務改善に積極的に関わってきた経験があります。

今回、プログラミング研修でWebアプリ開発の知識を学んだことで、「この現場の課題は、専用PCに依存しない仕組みを作れば解決できるのではないか」と気づいたことが、このアイデアが生まれた大きなきっかけになっています。

---

## 3. 課題の整理

### 3-1. 表に見えている困りごと

専用PCでしか映像を確認できず、他の人が使用中だと映像を見ることができない。また、トラブル発生時の映像共有には、現場の専用PCまで移動し、映像を探し、スマホで撮影し、メールに添付して自分のPCに送るという作業に約20分かかっており、非効率である。

### 3-2. 本当に解決したい課題

現状のフロー(移動→探す→撮影→転記→報告書作成)を続けることは、単なる時間の無駄にとどまりません。移動そのものに転倒災害などの安全リスクが伴い、また専用PCを映像探しのために占有することで、製造現場の本来の業務の妨げにもなっています。さらに、こうした「無駄だ」と感じる作業を日常的に繰り返すことは、従業員のモチベーション低下にもつながっています。

**本当に解決したい課題**: 専用PCに依存した映像確認・共有の仕組みが、時間・安全面・現場業務・従業員のモチベーションという複数の面で組織全体に負担をかけているという課題。

## 4. 想定ユーザー

### 4-1. ペルソナ

- **年齢**: 20代(入社数年目の若手技術員)。ベテラン技術員は現場PCを優先的に使う傾向があるが、若手技術員は遠慮してしまい、専用PCを使いたくても使いづらいと感じやすいため。

- **生活・状況**: 製造ラインの技術員として勤務し、トラブル対応やその報告書作成業務を日常的に担当。事務所からは徒歩5〜10分ほど離れた製造現場に足を運び、専用PCで映像確認する必要があるが、他の人が使用中の場合は待つか諦めるしかない。Webアプリがあれば、自席や現場のどのPCからでもすぐに映像確認・共有ができ、報告書作成の時間を大幅に短縮できる。

- **環境**: 製造現場と事務所が離れており(徒歩約5〜10分)、専用PCは現場に1台のみ設置されている環境。「1台しかない・現場でしか使えない」というハードルを、社内LAN経由でどのPCからでもアクセスできるWebアプリにすることで解消する。

### 4-2. 自分とユーザーの距離

私自身が製造ラインの技術員として、この課題に日常的に直面している当事者です。専用PCが使用中で映像確認ができない、トラブル対応時に20分もかけて映像を共有しなければならない、という状況を実際に何度も経験してきました。また、この悩みは自分だけのものではなく、同じ立場の同僚たちも同様に抱えている課題であり、現場に共通する課題であると確信しています。

### 4-3. 実際に使われる可能性

まずは自分自身が実際に使用し、操作性や利便性を実感した上で、その使用感を周囲に伝えていきます。使用しながら出てきた要望やバグは都度修正し、改善を重ねていく進め方を想定しています。トラブルが発生した瞬間や、現状の稼働状況を確認したいと思ったタイミングで、このアプリを使用すると考えられます。

現状はモバイル端末(iPad)からも映像を見ることは可能ですが、専用PCのようにトラブル画像を自動でブックマークする機能がないため、該当の映像を探すのにさらに時間がかかってしまいます。また、カメラシステムは製造ラインの列ごとに導入されており、別の列の映像を見たい場合はログアウト・ログインの切り替え操作が必要になる上、場合によっては該当の列の専用PCがある場所まで移動しなければなりません。Webアプリであれば、社内LAN上のどのPCからでも、列を意識せず必要な映像へすぐアクセスでき、トラブル画像のクリップ・共有もその場で完結できるため、これらの手間を大幅に削減できます。

### 4-4. 導入・継続の流れ

トラブルが発生した時だけでなく、設備の稼働状況を把握したい時、過去の映像を遡って分析したい時など、日常業務の様々な場面でこのサービスを利用する機会があると考えられます。

Webアプリはユーザーに紐づいたデータベース設計とし、各ユーザーが必要な画像・動画を自分のアカウント上に保存できる仕組みとします。利用開始にあたっては、社内アカウントでログインするのみで使い始められる形を想定しています。一時的な便利ツールではなく、日常業務に欠かせない業務上必須のアプリとして定着させることを目指します。

このアプリを業務で利用するには、サーバーとして運用するPCへのアクセスを社内セキュリティ部門に許可してもらう必要があり、これが導入における最大のハードルになると想定されます。この点については、社内Wi-Fi(社内LAN)を利用したローカルな環境で運用し、データが社外に一切出ない仕様とすることで、セキュリティ面の懸念を最小限に抑える設計を目指します。

## 5. 既存サービス・競合調査

### 5-1. 調査対象

- **サービス名**: NxWitness(現在使用中のシステムそのもの)
- **どんなことができるか**: サーバー・クライアント方式の監視カメラ管理システムであり、専用クライアントソフトをインストールしたPCから映像の閲覧・録画確認・ブックマーク作成などが可能。理論上はクライアントソフトをインストールするPCを増やせば、映像を閲覧できる場所を増やすことは可能。

### 5-2. それでも自分が作りたい理由

NxWitnessにはWebブラウザから映像を確認できる標準機能が存在せず、専用クライアントソフトをインストールしたPCでしか映像を閲覧できません。クライアントソフトを増やせば閲覧場所を増やすこと自体は理論上可能ですが、以下の理由により現実的ではありません。

- 社内で個人に支給されているPCには、セキュリティポリシー上クライアントソフトのインストールが禁止されている
- 多数のPCにクライアントソフトを導入し、社内環境(社内Wi-Fi)を利用すると、映像データの通信データが多く、通常業務に使用する通信帯域を逼迫させるおそれがある

こうした制約から、専用PCを増やすという解決策は現実的ではなく、既存のNxWitness提供のAPIを活用し、必要な情報だけを表示することができる軽量なWebアプリとして社内LAN上で提供する仕組みが必要だと考えました。

なお、上記のうち「多数のPCにクライアントソフトを導入し、社内環境(社内Wi-Fi)を利用すると通信帯域を逼迫させるおそれがある」という点については、本アプリでも通信量への配慮が必要となるため、8章で別途対策を整理しています。

### 5-3. 差別化ポイント

**製造ラインの技術員の、トラブル発生時に専用PCが使えず映像を確認・共有できない瞬間**を助けるアプリです。

専用PCへのアクセス制限や通信帯域の制約に縛られず、社内のどのPCからでも軽量なWebブラウザで映像確認・トラブル画像の共有ができる点が、既存の仕組みとの違いです。

## 6. 提供したい価値

### 6-1. ユーザーの変化

- **行動の変化**: トラブル発生時や稼働状況を確認したい時、現場の専用PCまで移動する必要がなくなり、社内LAN上のどのPCからでもその場で映像を確認・共有できるようになる。映像をアプリ上でクリップ・保存しておくことで、報告書作成もスムーズに行えるようになる。
- **気持ちの変化**: 「専用PCが使われていて確認できない」「移動や転記に時間を取られる」といったストレスから解放され、トラブル対応そのものに集中できるようになる。
- **考え方の変化**: 「トラブル対応は時間がかかって当たり前」という現状への諦めから、「必要な情報にすぐアクセスできて当然」という感覚へと変わっていく。

### 6-2. 価値提案

このサービスは、製造現場でトラブル対応にあたる技術員が、専用PCに縛られず、必要な映像をすぐに確認・共有できるようになるサービスです。

## 7. 実現する機能

### MVPで作る機能

MVPでは、優先度を以下のように整理して段階的に実装する。

**本リリースまでに必ず実装**

- ユーザー認証(社内アカウントによるログイン)
- ライブ映像の閲覧(Webブラウザ)
- 映像のクリップ・ブックマーク保存
- ユーザーごとのデータ保存(マイページ)
- 画像の一覧表示(静止画。通信帯域を圧迫しないための工夫)

**本リリースまでに可能な範囲で実装**

- 過去映像の検索・再生
- 過去動画の巻き戻し・早送り
- 各サーバー(カメラの列)の簡単な切り替え操作

**本リリースでは扱わない**

- トラブル報告書の自動生成・出力
- クリップの他ユーザーとの共有・コメント機能
- イベント発生時の通知機能

※ スコープ外の項目は、本リリース後の発展方針として9章で整理している。

### 認証・権限の考え方

- 社内LAN内での運用を前提とするが、URLを知っていれば誰でもアクセスできる状態は避けるため、アプリ側でユーザー認証を必須とする。
- クリップやブックマークなどユーザーが保存したデータは、原則として保存した本人のマイページからのみ閲覧できる設計とする(将来的な共有機能はスコープ外で検討)。
- 映像そのもの(ライブ・過去映像)は業務上共有される情報のため、ログイン済みユーザーであれば閲覧可能とする。

### 今後の方針

本リリースの段階では、新たな大きな機能追加は見据えていません。まずはMVPとして最低限必要な要件を満たした状態でプロトタイプをリリースし、実際に現場で運用しながらフィードバックを得て、改修を重ねていく方針です。

特に、直感的に操作できるUI(見た目だけで機能がわかるような、アイコンや配置の工夫)への改善を重視し、現場の技術員が迷わず使える状態を目指します。こうした地道な改善を積み重ねることで、一時的なツールではなく、現場に定着し日常的に使われるアプリへと育てていきたいと考えています。

## 8. 懸念点とその対策

**懸念点**: 本アプリは社内Wi-Fi(社内LAN)を利用して運用するため、映像データの通信によって社内ネットワークの通信帯域を逼迫させてしまう可能性がある。

**理由**: もともとNxWitnessの専用クライアントソフトを多数のPCにインストールできない理由の一つが「通信帯域の逼迫」であったことからも、映像データ(特にリアルタイムのストリーミング表示)は通信負荷が大きく、複数ユーザーが同時にアクセスした場合、社内ネットワーク全体のパフォーマンスに影響を与えるリスクがあると考えられる。

**対策**: MVPの段階では、リアルタイム性が必須ではない場面(稼働状況の確認や過去映像の一覧表示など)については、動画ではなく静止画ベースでの一覧表示を採用し、通信データ量を抑える設計とする。必要な場面(トラブル対応時の詳細確認など)に限定して動画再生を行うなど、用途に応じて通信量をコントロールする仕組みを検討する。運用開始後も、実際の通信負荷を計測しながら、画質や更新頻度の調整など継続的にチューニングを行っていく。

---

## 9. 今後の展開・発展の方向性

- **機能追加の方向性**: MVP運用を通じて現場からのフィードバックを集めながら、将来的にはトラブル報告書の自動生成・出力機能や、保存したクリップをチーム内で共有・コメントできる機能などを検討していきたい。特定のイベント発生時に通知を受け取れる仕組みも、稼働監視の効率化につながる可能性がある。
- **UI・体験の改善**: 運用しながら得られる現場の技術員からの声をもとに、より直感的に操作できるUIへ継続的に改善していく。若手・ベテラン問わず迷わず使えるよう、アイコンや画面配置のわかりやすさを追求していきたい。
- **機能以外の工夫**: データが蓄積されていくことで、過去のトラブル傾向を振り返る材料としても活用できる可能性がある。まずは自分の職場での運用実績を作り、他の製造ラインや他部署への展開も視野に入れていきたい。

## 10. 技術スタック

### 10-1. 使用技術

| 項目 | 内容 |
| --- | --- |
| フレームワーク | Django |

### 10-2. 技術選定の比較検討

| 候補 | 採用/不採用 | 理由 |
| --- | --- | --- |
| Django | 採用 | 研修で学んだ知識を活かせる、豊富な標準機能により開発効率が高い、Pythonを活用してNxWitness APIとの連携がしやすい |
| PostgreSQL | 採用 | Djangoとの相性が良く、信頼性・拡張性が高いため |
| Docker | 採用 | 社内オンプレミス環境でも一貫した環境構築・運用ができ、将来的なサーバー移行や複製にも対応しやすいため |

**デプロイについて**

社外にデータを一切出さない設計とするため、クラウドではなく社内オンプレミスのサーバーPCを設置し、そこにDocker環境を構築してアプリケーションを運用する方針です。

**今回チャレンジしたい点**

これまで学んできた技術をもとに、実際の業務課題を解決する実用的なアプリをゼロから構築すること。まずはNxWitness APIとの連携を実現し、将来的にはPLC等の制御データとも連携させることで、映像だけでなく設備稼働データも含めた統合的な現場支援ツールへ発展させていくことにも挑戦したい。

**不安な点**

開発にあたっては、AIを活用したコーディングを取り入れて制作を進める予定だが、その過程で生成されたコードすべてを完全には理解できないまま実装してしまう可能性がある点が不安である。作りながら仕組みや処理内容を都度確認し、理解を深めながら開発を進めていきたい。

### 10-3. キャッチアップ不足の懸念

使用するDjango・PostgreSQL・Dockerについては研修内である程度学習してきたが、NxWitness APIとの連携やPLCとの将来的な連携については未知の部分が多く、キャッチアップに一定の時間を要することが予想される。特にAPI仕様の理解や、実際の現場設備との接続検証には、想定より時間がかかる可能性がある点を懸念している。

このリスクに対しては、以下の順序で早い段階に検証を行い、本開発の見通しを立てる方針である。

1. NxWitnessが提供するAPIの公式ドキュメントの内容を確認し、本アプリで必要となる機能(ライブ映像取得・過去映像取得・ブックマーク操作など)が実現可能かを机上で確認する。
2. 検証用のクライアントから実際にAPIを叩き、映像取得・認証まわりの疎通確認を行う。
3. 上記で得られた制約(認証方式・レスポンス形式・帯域など)をもとに、MVPの機能範囲を最終確定させる。

まずはMVPとしてNxWitness APIとの連携に絞って開発を進め、PLC連携などの拡張は本リリース後、必要な検証を行った上で判断していく方針である。

### 本サービスの概要
本サービスは、製造現場の監視カメラ(NxWitness)映像を、専用PCに依存せず社内LAN上のPCからWebブラウザで確認・共有できるWebアプリです。専用PCが他の人に使用中で映像を確認できない、トラブル発生時の映像共有に約20分かかるといった、製造ラインの技術員が抱える非効率な業務フローの解消を目的としています。

想定ユーザーは、製造ラインで勤務し、トラブル対応や報告書作成を日常的に担当する20代の若手技術員です。専用PCの利用を遠慮しがちな立場にあり、本アプリによって、現場の専用PCに縛られず必要な映像へすぐアクセスできるようになります。

主な機能として、社内アカウントによるログイン認証、ライブ映像の閲覧、トラブル発生時の映像クリップ・ブックマーク保存、保存したクリップを管理するマイページ、通信帯域に配慮した静止画ベースの一覧表示を備えます。加えて、過去映像の検索・再生、巻き戻し・早送り、カメラ列(サーバー)の切り替え操作も実装範囲としています。

社内Wi-Fiを利用したローカル環境で運用し、データを社外に出さない設計とすることで、セキュリティ面の懸念にも配慮しています。

### 本サービスの概要（700文字以内）
本サービスは、製造現場の監視カメラ(NxWitness)映像を、専用PCに依存せず社内LAN上のPCからWebブラウザで確認・共有できるWebアプリです。専用PCが他の人に使用中で映像を確認できない、トラブル発生時の映像共有に約20分かかるといった、製造ラインの技術員が抱える非効率な業務フローの解消を目的としています。

想定ユーザーは、製造ラインで勤務し、トラブル対応や報告書作成を日常的に担当する20代の若手技術員です。専用PCの利用を遠慮しがちな立場にあり、本アプリによって、現場の専用PCに縛られず必要な映像へすぐアクセスできるようになります。

主な機能として、社内アカウントによるログイン認証、ライブ映像の閲覧、トラブル発生時の映像クリップ保存、保存したクリップを管理するマイページ、通信帯域に配慮した静止画ベースの一覧表示を備えます。加えて、過去映像の検索・再生、巻き戻し・早送り、カメラ列(サーバー)の切り替え操作も実装範囲としています。

社内Wi-Fiを利用したローカル環境で運用し、データを社外に出さない設計とすることで、セキュリティ面の懸念にも配慮しています。

### テーブル詳細
#### usersテーブル
- email : string / ログイン用メールアドレス(ユニーク制約)
- password : string / パスワード(暗号化して保存)
- name : string / 表示名

#### serversテーブル
- name : string / サーバー名(例: A列サーバー)
- address : string / 接続先アドレス(NxWitness API)
- line : string / 対象の製造ライン名

#### camerasテーブル
- server_id : bigint(FK) / 設置されているサーバー(serversを参照)
- name : string / カメラ名(例: 1号機正面カメラ)

#### clipsテーブル
- user_id : bigint(FK) / 保存したユーザー(usersを参照)
- camera_id : bigint(FK) / 取得元のカメラ(camerasを参照)
- title : string / クリップのタイトル
- file : string / 保存した画像・動画の実ファイル(パス)
- media_type : string / 種別('image' または 'video')
- taken_at : datetime / 映像取得日時
- memo : text / メモ・報告内容

### 補足(レビュー指摘への回答)
- カメラ情報はNxWitnessから都度取得するのではなく、camerasテーブルとしてDBで管理する方針とした(1サーバーに複数カメラが接続されるため)
- clipsはNxWitness側への参照ではなく、静止画・動画の実ファイルをアプリ側に保存する。NxWitness側のデータには影響を与えない
- 過去映像の検索・再生は、NxWitness側に保存されている録画をAPI経由でその都度参照する。保存したいものだけをclipsとして保存し、保存済みのclipsは アプリ内で再生可能とする
- ログインはemailのみを使用し、emailにユニーク制約を設ける。社員番号(number)は使用しない
-静止画・動画の実ファイルは、Webサーバー(アプリケーションサーバー)のストレージに保存する。
### 補足(ファイル実体の保存先・改訂)
静止画・動画の実ファイルは、Webサーバーのローカルディスクではなく、社内ネットワーク上のNASをネットワークドライブとしてマウントし、そこに保存する。これにより、Webサーバーの容量圧迫やデータ消失リスクを避ける。`clips.file`カラムには、NAS上の保存パス(文字列)のみを保持する。今回は、NASマウント方式で進め、必要に応じてセキュリティの許可がおりれば、AWS　S3等も将来的な選択肢として検討します
